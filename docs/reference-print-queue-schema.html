Print Queue Schema

The print server keeps its jobs, their history and the printer connection state in one SQLite file. Each job also has a folder of files on disk, frozen when the job comes in. This page shows that storage as the code builds it today, and what you should know before you change it, back it up or query it by hand.

Source: src/job_queue.py (class JobQueue) and src/job_artifacts.py (class ArtifactStore), with their callers in src/device_hub.py, src/http_api.py and src/scripts/print_server.py.

Entity diagram

Each box with a solid outline is one table. The dashed box is a folder on disk, not a table. A BLOB (binary large object) column has a tinted row. PK is the primary key. FK is a declared foreign key, a column that points to a row in another table.

On a phone, scroll the diagram sideways.

  • Solid line, one to many. One job has many job_events rows. The schema declares job_id REFERENCES jobs (id), and SQLite enforces it: the server turns on PRAGMA foreign_keys at each start, so an event for a missing job is refused. The pragma holds for one connection only. A sqlite3 shell does not enforce the key unless you turn it on there too.
  • Dashed line, no key. jobs.printer holds the same text as printers.id, but no constraint links them. The list of printers comes from the TOML config, not from this table.
  • Dashed line to the folder. The database stores no path. ArtifactStore.folder builds it from the job id: <database folder>/artifacts/<job id>/.
  • Not a column. The API field paper_mm is computed in each query as height / 8 (8 dots per mm). The database does not store it.

Job lifecycle

A job has one of six statuses. Two are live: queued waits for its printer, and sending is going to the device now. Four are final: printed, failed, expired and cancelled. One move leaves a final status: confirm takes a job cancelled while it was sending to printed, when the device prints it after all. A reprint makes a new job.

On a phone, scroll the diagram sideways. A double outline marks a final status. The dashed arrow is the one move out of a final status.

The code never runs VACUUM, and SQLite's default auto_vacuum is off. So the database file never shrinks. SQLite reuses the pages that a cleared jobs.data frees. The artifacts folder grows with every job and every reprint.

How a new job and its folder land together

  1. A worker thread writes the files into artifacts/.tmp-<random>/. If that fails, the sender gets 500 and nothing is queued.
  2. JobQueue.add (or reprint) opens a BEGIN IMMEDIATE transaction, inserts the job and its events, and renames the folder to the job id (_placing).
  3. The transaction commits. If the insert, the rename or the commit fails, the transaction rolls back and _placing deletes the renamed folder. The API deletes a folder that is still staged. The sender gets 500, and no job and no folder remain.
  4. At each start, the server deletes every .tmp-* folder.

One gap remains. A crash after the rename and before the commit leaves a folder that no job names. Nothing reads or deletes it. A later job that draws the same 8-character id then fails its rename and is refused with 500.

Design points worth knowing

Concurrency

One process, one connection, one thread

JobQueue.__init__ opens one sqlite3 connection in autocommit mode (isolation_level=None). All calls come from the asyncio event loop thread. The worker threads (asyncio.to_thread) render images and write the staged artifact files; they do not touch the database. The rename into place runs on the event loop thread, inside the transaction.

No two queue calls ever overlap. But each query blocks the whole server while it runs, so a slow query delays every device and HTTP request.

Transactions

BEGIN IMMEDIATE around each change

JobQueue._transaction wraps every method that writes more than one statement, and the reads that expire jobs first (job, jobs, stats). It takes the write lock at the start. On any exception, a failed COMMIT included, it rolls back, so a later COMMIT cannot store half a change. update_printer_state, printer_state, activity and the reads in stats after its expiry step run as single autocommit statements.

A job's status and its events always change together, and a new job commits together with its folder name.

SQLite settings

WAL, a 2-second busy timeout, foreign keys on

JobQueue._open sets journal_mode = WAL (write-ahead log) and foreign_keys = ON at each start. The connection waits up to BUSY_TIMEOUT_SECONDS, 2 s, for a write lock that another program holds. In WAL mode, readers and the writer do not block each other. Only a second writer blocks.

A sqlite3 shell can read while the server runs. Do not leave a write transaction open in it. Most queue calls take the write lock, reads too, because they expire jobs first. Each one then waits 2 s with the event loop stopped, so every device and HTTP request waits too. One admin poll makes several calls, so one stall costs several timeouts. The timeout is small to keep that sum far below the 60 s device receive timeout.

Ids

Short random job ids, sequential event ids

_new_id returns secrets.token_hex(4): 8 hex characters, 32 random bits. _insert tries again on a primary-key collision, up to 5 times, then raises. The job's folder takes the same id. job_events.id is an INTEGER PRIMARY KEY, which SQLite numbers in insert order.

A job id is short enough to read off paper. It carries no order, so sort jobs by created_at.

Time

REAL Unix seconds; "today" uses the server's time zone

Every time column is a REAL: seconds since 1970-01-01 UTC, with fractions, from time.time(). No zone is stored. stats and activity compute "today" from midnight in the server's system zone, because the HTTP API passes no tz.

If you move the server to another zone, the stored data stays correct, but the "today" counts change. Use datetime(created_at, 'unixepoch') in SQL to read a time.

Expiry

Expiry is lazy

No dedicated timer expires jobs. _expire runs as the first step of most queue calls, and it expires the queued jobs of every printer. While a printer is connected and not paused, its delivery loop calls take at least every 30 s (RECHECK_INTERVAL). The expired event has at set to the job's expires_at, not to the time it noticed.

In raw SQL, a job past its expiry can still show queued, most often when no printer is connected. The API is correct, because it calls _expire first.

Indexes

Some frequent queries scan the whole table

I ran EXPLAIN QUERY PLAN on each query, with real status values, on an empty copy of the schema (SQLite 3.50.4, no ANALYZE). These use an index: take, _expire, clear, move, the lookups by id, one job's events, activity, the queued count, and jobs or stats for one printer. These read every row: jobs with no filter (the admin list) and jobs with only a status filter, the printed-jobs query and the printer-name list in stats for all printers, the 24-hour failed count for all printers (it scans all of job_events), and release_all (only at start). The failed count for one printer reads every job of that printer.

Rows are never deleted, so these scans grow with history. I did not measure timings, and plans on real data can differ.

Restart

Jobs in flight go back to the queue

On a clean stop, DeviceHub.shutdown cancels each delivery, and _deliver releases the job with the detail "server shutdown". After a crash, the job stays sending in the file. At the next start, DeviceHub.start calls release_all. Each such job goes back to queued, or to failed if it used 3 attempts, or to expired if it is past its expiry. The start also deletes the .tmp-* staging folders.

A ticket that printed but had no confirmation yet prints again after a restart. The interrupted attempt counts toward the limit of 3.

Versioning

Schema version in PRAGMA user_version

SCHEMA_VERSION is the length of _MIGRATIONS, now 1. Step n takes a database from version n to n + 1. Version 0 is the schema from before versioning. At each start, JobQueue._open reads the version before any write, also before it sets WAL. A newer version raises SchemaTooNew. The server then exits with code 1 and prints "Cannot open the job database <path>: its schema version is N, and this server knows versions up to 1. Run a newer server, or restore a backup from before the upgrade."

Otherwise, in one transaction, a file with no jobs table gets _SCHEMA. Any other file gets each step from its version up. Then the version becomes SCHEMA_VERSION. The step from 0 (_from_unversioned) runs every CREATE … IF NOT EXISTS in _SCHEMA and drops the png column if it exists.

To change the schema, edit _SCHEMA and append a step to _MIGRATIONS. A database at the current version never runs _SCHEMA again, so a change made only there reaches new files but not existing ones. The step from 0 deletes the old PNG images; it does not move them into folders. A job without a folder has no image (404) and cannot be reprinted (409).

Backups

Back up the database with .backup, then the artifacts folder

The database is the file named by database in the [server] table of the TOML config. A relative path is relative to the config file's folder. The server creates the parent folder at start. In WAL mode the file has two companions, <name>-wal and <name>-shm. Committed writes can stay in the -wal file until SQLite copies them into the main file. The artifacts folder sits beside the database file. The repo has no backup script.

While the server runs, use sqlite3 <database> ".backup <copy>". It uses SQLite's online backup, which also reads the writes in the -wal file. Then copy the artifacts folder: in this order, a job added in between gets a spare folder, not a missing one. Never copy the main file without its -wal file, because the copy can miss committed jobs. recommendation, restore not tested here

Surprise

A cancelled job can still print

cancel and clear accept a sending job. The hub already holds the bytes in memory and keeps sending them. After the cancel, mark_sent does nothing, so no sent event appears. If the device then confirms, confirm moves the job from cancelled to printed, with the detail "after the cancel" on its printed event. If the delivery fails, release does nothing and the job stays cancelled.

A cancel does not stop paper that is on its way, but the job detail shows what happened. confirm accepts any cancelled job. Only the hub, which confirms just the job it is delivering, keeps a job cancelled while queued from becoming printed.

Surprise

The printers table is not the printer list

The config defines the printers. The table only keeps connection state, and it keeps rows for removed printers. jobs.printer has no key. The move API returns 404 for a printer that is not in the config.

If you remove a printer from the config, its queued jobs stay until they expire, and you cannot move them with the API.

Detail

Smaller things

  • _release checks the attempt count before the expiry. A third-attempt job past its expiry becomes failed, not expired.
  • sent_at is not cleared when a job goes back to queued. It holds the time of the latest send.
  • size_bytes and frames stay after data is cleared, so the history keeps the job size.
  • A reprint's meta.json keeps the original's template and web_dist_sha256, with a new created_at and reprint_of.
  • The code uses RETURNING, window functions and ALTER TABLE … DROP COLUMN, so it needs SQLite 3.35 or newer. The workspace's Python links SQLite 3.50.4. I did not check the deployed server's Python.
