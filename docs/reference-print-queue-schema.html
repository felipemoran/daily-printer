Print Queue Schema

The print server keeps its jobs, their history and the printer connection state in one SQLite file. This page shows that schema as the code builds it today, and what you should know before you change it, back it up or query it by hand.

Source: src/job_queue.py (class JobQueue), with its callers in src/device_hub.py, src/http_api.py and src/scripts/print_server.py. Where the docs and the code disagree, this page shows the code and flags the difference.

Entity diagram

Each box is one table. A BLOB (binary large object) column has a tinted row. PK is the primary key. FK is a declared foreign key, a column that points to a row in another table.

On a phone, scroll the diagram sideways.

  • Solid line, one to many. One job has many job_events rows. The schema declares job_id REFERENCES jobs (id), but SQLite does not enforce it, because the code never turns on PRAGMA foreign_keys.
  • Dashed line, no key. jobs.printer holds the same text as printers.id, but no constraint links them. The list of printers comes from the TOML config, not from this table.
  • Not a column. The API field paper_mm is computed in each query as height / 8 (8 dots per mm). The database does not store it.

Job lifecycle

A job has one of six statuses. Two are live: queued waits for its printer, and sending is going to the device now. Four are final: printed, failed, expired and cancelled. Nothing moves a job out of a final status. A reprint makes a new job.

On a phone, scroll the diagram sideways. A double outline marks a final status.

The code never runs VACUUM, and SQLite's default auto_vacuum is off. So the file does not shrink after a prune. SQLite reuses the freed pages for new rows.

Design points worth knowing

Concurrency

One process, one connection, one thread

JobQueue.__init__ opens one sqlite3 connection in autocommit mode (isolation_level=None). All calls come from the asyncio event loop thread. The worker threads (asyncio.to_thread) only render and convert images; they do not touch the database.

No two queue calls ever overlap. But each query blocks the whole server while it runs, so a slow query delays every device and HTTP request.

Transactions

BEGIN IMMEDIATE around each change

JobQueue._transaction wraps every method that writes more than one statement. It takes the write lock at the start and rolls back on any exception. prune, update_printer_state, printer_state, png, activity and the reads in stats run as single autocommit statements.

A job's status and its events always change together. You never see a status without its event.

Journal mode

Rollback journal, not WAL

The code sets no PRAGMA. A fresh file reports journal_mode = delete, the SQLite default, not WAL (write-ahead log). The connection uses Python's default 5-second busy timeout.

In this mode an open read in another program blocks the server's commits. If a read transaction stays open for more than 5 seconds (for example a BEGIN left open in the sqlite3 shell), server calls fail with "database is locked".

Ids

Short random job ids, sequential event ids

_new_id returns secrets.token_hex(4): 8 hex characters, 32 random bits. _insert tries again on a primary-key collision, up to 5 times, then raises. job_events.id is an INTEGER PRIMARY KEY, which SQLite numbers in insert order.

A job id is short enough to read off paper. It carries no order, so sort jobs by created_at.

Time

REAL Unix seconds; "today" uses the server's time zone

Every time column is a REAL: seconds since 1970-01-01 UTC, with fractions, from time.time(). No zone is stored. stats and activity compute "today" from midnight in the server's system zone, because the HTTP API passes no tz.

If you move the server to another zone, the stored data stays correct, but the "today" counts change. Use datetime(created_at, 'unixepoch') in SQL to read a time.

Expiry

Expiry is lazy

No timer expires jobs. _expire runs as the first step of most queue calls. It writes the expired event with at set to the job's expires_at, not to the time it noticed.

In raw SQL, a job past its expiry can still show queued. The API is correct, because it calls _expire first.

Indexes

Some frequent queries scan the whole table

I ran EXPLAIN QUERY PLAN on an empty copy of the schema (SQLite 3.51.0, no ANALYZE). These use an index: take, _expire, the queued count, one job's events, activity, and jobs or stats for one printer. These scan every row: jobs() with no filter (the admin list), the printed-jobs query in stats() for all printers, the 24-hour failed count (it scans all of job_events), release_all (only at start) and prune (daily).

Rows are never deleted, so these scans grow with history. I did not measure timings, and plans on real data can differ.

Restart

Jobs in flight go back to the queue

On a clean stop, DeviceHub.shutdown cancels each delivery, and _deliver releases the job with the detail "server shutdown". After a crash, the job stays sending in the file. At the next start, DeviceHub.start calls release_all. Each such job goes back to queued, or to failed if it used 3 attempts, or to expired if it is past its expiry.

A ticket that printed but had no confirmation yet prints again after a restart. The interrupted attempt counts toward the limit of 3.

Versioning

No schema version, no migrations

The server runs _SCHEMA at each start with CREATE TABLE IF NOT EXISTS. Nothing reads or writes PRAGMA user_version, and no ALTER TABLE exists in the code.

If you add or drop a column in _SCHEMA, an existing file keeps its old shape, and the queries then fail on it. The first schema change needs a migration step.

Backups

Copy one file, safely

All state is in the file named by database in the [server] table of the TOML config. A relative path is relative to the config file's folder. The server creates the parent folder at start. During a write, SQLite also keeps a <name>-journal file beside it. The repo has no backup script or backup docs.

A plain file copy during a write can be torn. Stop the server first, or use sqlite3 <file> ".backup <copy>", which uses SQLite's online backup. recommendation, not tested here

Surprise

A cancelled job can still print

cancel and clear accept a sending job. The hub already holds the bytes in memory, so the device can still print the ticket. confirm then does nothing, because it requires sending. No printed event is written.

The admin page can show cancelled for a ticket that is on paper.

Surprise

The printers table is not the printer list

The config defines the printers. The table only keeps connection state, and it keeps rows for removed printers. jobs.printer has no key. The move API returns 404 for a printer that is not in the config.

If you remove a printer from the config, its queued jobs stay until they expire, and you cannot move them with the API.

Detail

Smaller things

  • _release checks the attempt count before the expiry. A third-attempt job past its expiry becomes failed, not expired.
  • sent_at is not cleared when a job goes back to queued. It holds the time of the latest send.
  • size_bytes and frames stay after data is cleared, so the history keeps the job size.
  • The code uses RETURNING and window functions, so it needs SQLite 3.35 or newer. I did not check which SQLite the server's Python links.
PLANNED, NOT BUILT

Changing now: frozen ticket artifacts

Another builder works on task axvgf8 ("Freeze every ticket's artifacts at creation"). Nothing below is in the code yet. The task record says: keep each ticket as it was created, so a later template, font or code change never alters past tickets.

  • Each job gets a folder: <database folder>/artifacts/<job-id>/.
  • The folder holds payload.json (the input), page.mhtml (the rendered page), screenshot.png (the raw capture), print.png (the final printed image), job.escpos (the printer bytes) and meta.json.
  • The artifacts are kept forever. There is no automatic prune.
  • SQLite stays the index of jobs.
  • The png BLOB column and its 30-day prune will probably be removed.
  • A reprint copies the folder and records reprint_of.

What this means for the schema. It is the first change to an existing table, and no migration mechanism exists (see Versioning above). Backups must then include the artifacts folder as well as the database file. The folder grows without limit.

Flags: docs against code

I compared the code with the "Job lifecycle" and "Interfaces" sections of docs/planning-print-system-architecture.md. The docs do not describe the tables, so no column conflicts. These statements differ from the code:

"A job not confirmed before its expiry is dropped."

Code: a queued job becomes expired only when a queue call runs _expire. A job in sending expires only when it is released; if the device confirms it late, it is printed. "Dropped" means the bytes are cleared; the row stays.

"The server sends an unconfirmed job again when the device reconnects."

Code: release puts the job back in the queue at once. After a device error reply, the same connection sends it again after a 60-second pause. A reconnect is not needed.

"The rendered PNG stays for 30 days."

Code: the prune runs once at start and then every 24 hours, so a PNG stays 30 to about 31 days. The prune ignores the job status.

Printer state "kept by the server"

The docs list 15 fields. Only 7 of them (id and 6 state fields) are in the printers table. name, place and public come from the config, and queued and printed_today are computed. online, current_job and paused_until are in memory and reset on restart. This is a gap in the docs, not a conflict.

Job record lists paper_mm

The API returns it, but it is computed as height / 8 in each query, not stored. A minor point.
